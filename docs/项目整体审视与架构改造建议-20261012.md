# 福福学堂整体审视与架构改造建议

审视日期：2026-10-12。范围包括学习端、后台、浏览器游戏、Python 服务、MySQL、内容源文件、素材、脚本和本地运行方式。项目是持续迭代中的家庭学习产品，以下建议以保留现有功能、内容和网址为前提。

## 当前项目地图

| 区域 | 当前职责 | 观察 |
|---|---|---|
| `frontend/` | 原生 HTML、CSS、JavaScript 学习端和后台；静态资源与部分内嵌小游戏 | 无前端构建步骤，入口清晰；随着功能增加，单页、全局样式和脚本间依赖已经变多 |
| `backend/server.py` | `SimpleHTTPRequestHandler` 静态服务、REST 路由、认证、学习流程、题库与积分等 | 约 1,578 行；使用多重继承路由 mixin，应用组装、接口分发和业务处理集中在一个入口 |
| `backend/*` | MySQL 访问、内容目录、学习领域、游戏、社区和管理模块 | 约 36 个 Python 文件；领域模块各自管理部分表结构，初始化规则此前与离线初始化脚本不一致 |
| `content/` | 可审核的 JSON、题库源、游戏原始代码与许可记录 | 游戏源 402 个文件；学习、题目、故事等分散在多个子目录，部分数据另有 MySQL 运行时副本 |
| `frontend/assets/` | 图片、音频、视频、模型、游戏运行文件、用户上传内容 | 运行素材规模较大；`frontend/assets/` 中若干内容目录被 Git 忽略，源码备份不会自动包含全部运行素材 |
| `scripts/` | 初始化、生成、导入、发布、校验、备份和一次性操作 | 约 287 个文件挤在一个目录，其中约 58 个测试、18 个校验和 40 个构建脚本，入口难以发现 |
| `docs/`、`artifacts/`、`logs/` | 功能说明、实施记录、生成产物、运行日志 | 文档较丰富，但按时间和单次功能积累，缺少一份持续更新的系统地图和统一操作入口 |

学习端主要入口是学习首页、故事科普、探索实验室、积分商店、游戏乐园。首页以外还包括学科练习、学习卡片、故事/科学、诗词、朝代与人物、战役和三十六计、地理、太阳/月球/地球、工程与远古生命、农场/动物园、亲子账户及共创社区。后台集中管理用户、评论、学习题目、故事、图文与 3D 专题等。游戏资源既有项目自制内容，也有移植项目及其原始代码、许可和适配副本。

主要数据关系已经存在：MySQL 是学习账号、档案、答题、积分和大部分已发布内容的运行时来源；`content/` 保存许多可审阅或可重新导入的源稿；`frontend/assets/` 保存媒体。题库已使用草稿/发布、分页和服务端判题；新式图文与 3D 内容使用素材登记及章节/分段关联。这些是继续改造的基础，不建议推倒重做。

## 本次已经完成的架构改造

原先服务启动会初始化故事、卡片、历史、地理、社区、游戏等全部模块；单独运行 `scripts/init_backend_db.py` 却只初始化故事、内容目录、学习库、农场和玩具游戏。这样会让“我已执行数据库初始化”与实际服务依赖不一致。

现已新增 [backend/startup.py](../backend/startup.py)，将服务使用的完整初始化顺序和农场商品补齐集中到 `initialize_application()`。服务启动和离线初始化脚本都调用同一函数，消除了两套清单漂移。初始化脚本原有“幂等准备数据库”的用途与后续动物园补种说明保留。此改动不触碰页面、内容记录、数据库数据或视觉设计。

## 架构判断与主要风险

### 需要优先处理

1. **数据库结构没有统一版本账本。** 多个模块在 `initialize()` 中创建表、补字段或修数据，`server.py` 再负责按固定顺序调用。即使本次统一了调用入口，迁移的历史版本、失败恢复、执行记录和回滚办法仍然分散。下一步应建立有序迁移目录和 `schema_migrations` 记录；旧初始化逻辑先作为兼容迁移逐步收拢，确认备份与恢复后再移除。
2. **内容“源稿”和“运行库”容易混淆。** 一类内容在 JSON/脚本中维护，另一类直接在后台改 MySQL；有些初始化只补缺，不覆盖数据库编辑，有些导入采用版本号或迁移键。每一种内容都应明确唯一权威源、发布方式、冲突策略、撤回方式和媒体依赖，并由后台标明“草稿 / 已发布 / 源文件版本”。
3. **上传素材和数据库需要一起备份。** 文档中的上传素材在 `frontend/assets/content/`，但该目录受 Git 忽略规则影响，数据库备份并不包含文件本身。应提供一个同一时间点的“数据库 + 用户上传媒体”备份和恢复流程，并定期验证能恢复，而不只是确认备份文件存在。
4. **运行服务默认监听所有网卡并使用普通 HTTP。** 这便于家庭局域网设备使用，但用户账号、登录会话和评论数据经过局域网时没有传输加密。管理接口目前只接受本机回环请求；这是有效的边界，但也意味着远程平板不能直接管理。需要在准备公网或远程管理之前，明确部署方式（反向代理 HTTPS 或 VPN）、cookie 的 `Secure` 属性、可信代理配置和管理入口策略。
5. **认证防护需要补齐验证。** 密码使用 PBKDF2-SHA256 摘要，会话 cookie 设置 HttpOnly 与 SameSite=Lax；目前代码中未发现登录失败限速机制，cookie 未设置 Secure。上线前应加入按账号与来源的节流、会话撤销/过期检查、CSRF/Origin 策略测试，并检查密码重置和管理员首次创建流程。

### 中期演进建议

6. **`server.py` 承担太多职责。** 继续把新接口放在中央 `do_GET` / `do_POST` 分支会提高改动冲突和误操作概率。保持现有 Python 与原生前端，先把 URL 路由和认证/权限中间步骤抽出来，再按学习、内容、账户、游戏、社区划分服务层；每一步保留原 URL 与响应结构并加接口回归。当前路由 mixin 可以作为过渡，不必一次性换框架。
7. **旧 SQLite 兼容层与 MySQL 运行层仍然并存。** `backend/db.py` 与 `mysql_learning_db.py` 同时存在；MySQL 层还要改写早期 SQL 写法。应先盘点仍在使用的迁移入口和遗留数据，明确 SQLite 的最终退出条件，再拆除兼容层；在完成数据校验前保留它，不做直接删除。
8. **前端模块边界和缓存版本依赖人工维护。** 原生脚本的入口有大量 `<script>` 引用，CSS 主文件约 107 KB，页面脚本与共享状态相互依赖，缓存版本参数需要手动改。建议先建立页面/功能依赖清单和统一版本常量；以后新增代码按功能目录组织、对外提供初始化入口，避免把内容和新逻辑继续堆入 `app.js` 或主样式文件。若采用打包工具，应单独评估部署收益和开发者维护成本，不作为第一步强制迁移。
9. **运维脚本缺少清楚的分组和标准检查入口。** 生成、导入、发布、检查和历史一次性脚本混在 `scripts/`。建议分为 `scripts/content/`、`scripts/ops/`、`scripts/maintenance/`，测试移入 `tests/` 并提供一个总检查命令；移动前先盘点 README、文档、批处理和 PowerShell 的引用，保留兼容转发脚本以免破坏老用法。
10. **大型游戏与媒体的发布成本缺少统一边界。** 上游源码、适配版、线上运行资源、许可文件、生成物有时分别位于 `content/`、`frontend/assets/`、`artifacts/`。为每个第三方游戏/大型媒体保留来源 URL、许可证、上游版本、校验和、构建步骤、应用路径与资源体积；明确哪些必须随版本发布，哪些只作归档。模型和音视频应按需加载并有体积预算。
11. **测试存在但不够集中。** 已有静态检查、HTTP 验证、构建和页面交互脚本；需逐步形成不依赖线上数据库的快速检查，以及有明确测试数据库的接口集成检查。重点覆盖权限矩阵、内容发布与撤回、儿童端答案不可见、积分重复提交、素材路径和学习记录归属。
12. **内容质量需要纳入发布流程。** 题目、历史、诗词、图片与音频现在有单独来源和许可记录。建议按内容类型定义字段完整性、引用/来源、年龄适配、音视频存在性和关联完整性检查；由审核通过后发布，校验失败时不进入学习端。文化/历史内容由事实来源校验，生成素材的说明不得冒充历史实物复原。

## 建议目标结构

建议保留“单一可部署应用”，先让边界清晰，再考虑拆服务：

```text
frontend/
  pages/              页面入口与组合
  features/           learning, stories, history, games, community
  shared/             API、登录状态、媒体、通用交互
backend/
  api/                路由、输入校验、认证和授权
  domains/             accounts, learning, content, games, community
  repositories/        MySQL 查询和事务
  migrations/          按版本顺序执行的数据库迁移
content/               可审阅源稿、导入格式、许可与来源
media/                 有版本、有备份策略的发布素材
scripts/
  content/ ops/ maintenance/
tests/                 unit, integration, browser
docs/                  架构地图、内容流程、备份恢复、发布手册
```

目录是目标方向，不代表本次需要立即移动全部文件。架构原则应为：接口层校验输入并落实权限；领域模块实现规则；repository 负责数据库读写；迁移工具负责结构变化；导入器只处理有明确版本和来源的源稿；前端 API 客户端统一处理错误、登录状态和缓存。继续保持一个 Python 服务和一个 MySQL 实例，等容量或部署需求证明有必要时再拆分。

## 推荐实施顺序

| 顺序 | 交付 | 主要验收 |
|---|---|---|
| 1（已完成） | 服务与离线脚本共用完整初始化流程 | 两种启动路径调用同一个初始化函数，模块顺序一致；Python 语法检查通过 |
| 2 | 数据备份/恢复覆盖上传媒体 | 备份清单记录数据库与媒体时间点；在隔离目录恢复并抽查故事、卡片、上传媒体 |
| 3 | 数据库迁移账本与迁移命令 | 新库、当前库、重复执行、失败重试、回滚/前滚说明全部验证；先影子运行，不删旧逻辑 |
| 4 | 内容源与发布规则登记 | 每种内容列明权威源、导入键、编辑冲突规则、撤回和备份；后台与文档一致 |
| 5 | 认证和远程访问加固 | 限速、HTTPS/代理、cookie、CSRF/Origin、管理员访问路径通过自动检查；家庭局域网设备回归 |
| 6 | API 路由分层 | 保持接口兼容，分批迁移模块；每个域有权限和响应契约测试 |
| 7 | 前端边界与资源策略 | 页面依赖图、统一缓存版本、按需媒体加载、低端平板性能检查 |
| 8 | 脚本和测试归档 | 可发现的命令入口、迁移后的旧命令兼容、快速与集成测试分离 |

## 审美与体验问题（B 方向已确认并实施）

1. 学习端当前使用暖白底、灰绿主色、金色点缀、圆角卡片和团团插画/表情符号，整体轻松、友好，适合低龄孩子。与此同时，部分 3D 专题、移植游戏、科学视频、黏土内容各自沿用来源项目的画面语言，跨页面切换时一致性不完全相同。
2. 主页把语文、数学、英语、科学、故事、探索、积分、游戏和团团等多种入口同时呈现。功能丰富，但新用户需要理解“学科卡片”“快速练习”“故事科普”“探索实验室”的差别；建议用任务分组和清晰的推荐路径减轻选择负担。此项会调整信息层级和首页布局，需要你确认方向。
3. 后台曾出现密集布局和过小字号，近期已增加“你现在想做什么”快捷入口并放大主要文字、字段和按钮；目前后台仍保留左侧多栏目、列表/编辑器并列等管理工具模式。是否继续简化侧栏、命名和页面层级属于审美/交互取舍，暂不代你决定。
4. 不同专题的字号、间距、圆角和操作按钮此前未共享统一规范。本次按 B 方向新增 `frontend/content-consistency.css` 并在学习端与管理后台共同加载：统一内容标题/正文层级、故事与学习卡片留白、搜索输入框和主要按钮高度、后台字段控件及连接状态文字；首页明确分组为课本/学科练习、故事、探索三个视觉区块，并适配手机与平板；保留历史专题的金色细节、科学手绘画面和品牌配色。
5. taste-skill 强调保护品牌、导航、文案和无障碍，也明确将密集后台面板排除在其主要适用范围之外。本项目是原生 HTML/CSS/JS，因此借鉴其审计与一致性方法，没有自动迁移 React/Tailwind 模板、添加暗色模式或套用营销页规则。
6. 第三方游戏运行在独立资源/iframe 中，特色 3D 场景有独立 CSS 与场景控制；本次一致性样式限定在学习内容组件与后台，未修改游戏或 3D 文件。
7. 浏览器回归检查覆盖 1440、768、390px 三种视口：主页面和后台均加载新样式，无水平溢出或 JavaScript 页面错误；管理员未登录时只显示认证界面，因此后台表单的实际交互仍需在已有管理员会话中复核。
